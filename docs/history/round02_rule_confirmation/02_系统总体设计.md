# 02 系统总体设计

本文件描述“校园食光 CampusBite”的总体设计。本轮仅做设计，不编写前后端业务代码。

## 1. 总体架构

建议采用前后端分离的轻量架构：

- 前端：Vue 3 + Vite + Element Plus，负责页面展示、表单输入、筛选条件交互、异常提示和推荐结果展示。
- 后端：Python + FastAPI，负责提供餐饮数据接口、详情接口、推荐接口和输入校验。
- 数据库：SQLite，保存模拟餐厅、窗口或菜品数据。
- 推荐算法：后端实现硬约束过滤 + 多维加权评分，返回排序后的 Top 3-5 结果和可解释推荐理由。

该架构符合老师“技术栈不限、建议先完成 MVP”的要求，也便于本地运行、截图和记录 AI 辅助开发过程。

## 2. 数据流

1. 用户在前端输入关键词、预算、口味、距离、评分、营业状态、用餐时段和忌口等条件。
2. 前端对明显非法输入进行基础提示，例如预算不是数字、距离为负数。
3. 前端调用后端接口。
4. 后端进行参数校验和标准化。
5. 后端从 SQLite 读取模拟数据。
6. 后端先执行硬约束过滤，排除预算不符、忌口冲突、营业状态不符等结果。
7. 后端对剩余结果进行加权评分。
8. 后端生成与数据字段一致的推荐理由。
9. 后端返回 Top 3-5 推荐结果。
10. 前端展示结果、评分、标签、推荐理由和详情入口。
11. 若无结果或接口失败，前端展示友好提示和调整建议。

## 3. 功能模块设计

### 3.1 餐饮数据展示模块

输入：

- 用户打开页面。
- 可选的分页、排序或默认展示条件。

处理逻辑：

- 前端调用数据列表接口。
- 后端读取不少于 20 条模拟数据。
- 数据字段缺失时，后端返回可识别的默认值或标记；前端避免空白崩溃。

输出：

- 餐饮列表，显示名称、位置、菜系或口味、人均价格、营业时间、距离、评分等信息。
- 页面醒目位置展示“模拟数据/非实时数据”说明。

### 3.2 搜索与筛选模块

输入：

- 关键词。
- 预算上限。
- 口味标签。
- 最大距离。
- 最低评分。
- 营业状态。
- 用餐时段。
- 忌口食材。
- 排序方式。

处理逻辑：

- 关键词匹配名称、位置、菜系、口味、推荐标签等字段。
- 筛选条件至少支持 4 种，建议实现预算、口味、距离、评分、营业状态、忌口和排序。
- 数值输入进行边界校验。
- 空条件时返回默认列表或默认推荐，不报错。

输出：

- 符合条件的列表。
- 若无匹配结果，展示可操作建议，例如“放宽预算、减少忌口或扩大距离范围”。

### 3.3 个性化推荐模块

输入：

- 用户偏好表单：预算、口味偏好、距离偏好、是否只看营业中、最低评分、忌口、用餐时段。

处理逻辑：

- 先应用硬约束：
  - 菜品 `price` 高于预算的结果直接排除；餐厅 `avg_price` 不参与菜品预算判断。
  - 包含忌口食材的结果必须排除。
  - 用户选择“只看营业中”时，非营业结果必须排除。
  - 距离超过用户设定上限的结果排除。
- 再执行加权评分：
  - 预算内菜品价格越低，价格适配分越高：`P = 100 × (1 - price / budget)`；`budget <= 0` 为非法输入。价格分只作为综合分的一部分。
  - 口味标签匹配越多，口味得分越高。
  - 距离越近，距离得分越高。
  - 评分越高，评分得分越高。
  - 营业中可获得额外得分。
- 取总分最高的 Top 3-5。
- 为每条结果生成解释，解释只能使用真实字段和实际命中的规则。

输出：

- Top 3-5 推荐结果。
- 每条结果包含总分、关键标签和推荐理由。
- 若不足 3 条，按实际数量展示，并提示条件较严格。

### 3.4 详情查看模块

输入：

- 用户点击某个餐厅、窗口或菜品。

处理逻辑：

- 前端根据 ID 请求详情接口。
- 后端返回完整字段。
- 若 ID 不存在，返回 404 类错误，前端展示友好提示。

输出：

- 详情弹窗或详情页。
- 展示名称、位置、菜系/口味、人均价格、营业时间、距离、评分、推荐标签、忌口风险、数据更新时间等信息。

### 3.5 异常处理模块

输入：

- 空输入。
- 非法预算、非法距离、非法评分。
- 无匹配结果。
- 数据字段缺失。
- 后端接口失败。

处理逻辑：

- 前端和后端都进行输入校验。
- 后端返回统一错误结构。
- 前端根据错误类型显示中文提示。
- 字段缺失时采用默认展示，例如“暂无数据”，并避免推荐理由引用缺失字段。

输出：

- 程序不崩溃。
- 用户能理解发生了什么，并知道如何调整。

### 3.6 数据说明模块

输入：

- 页面加载。

处理逻辑：

- 在首页、推荐结果区或页脚显示数据说明。
- 数据说明应包含“模拟数据”“非实时营业信息”“仅用于课程项目演示”等信息。

输出：

- 用户明确知道数据限制。

## 4. 数据模型初步设计

经第二轮人工确认，采用 `restaurants` + `dishes` 双表与外键；菜品为主要推荐对象，餐厅/窗口作为关联展示信息。以下字段按所属表保存，查询时关联展示，不能混淆两个表的 ID 或价格。

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| id / restaurant_id | integer | 两表各自的主键；菜品 restaurant_id 外键指向场所。 |
| name | string | 名称，用于展示和搜索。 |
| type | string | restaurants 字段，restaurant/window；dishes 表表示菜品。 |
| location | string | 校园位置或食堂楼层。 |
| cuisine | string | 菜系，如川菜、面食、轻食。 |
| taste_tags | array/string | 口味标签，如微辣、清淡、甜口。 |
| avg_price / price | number | restaurants.avg_price 为参考人均价；dishes.price 为菜品价格，仅后者参与预算过滤；金额单位为元。 |
| business_hours | string | 营业时间展示文本。 |
| meal_periods | array/string | 早餐、午餐、晚餐、夜宵等。 |
| is_open | string enum | TRUE/FALSE/UNKNOWN；由模拟时段或明确模拟状态判定；UNKNOWN 不得视为营业。 |
| distance_m | number | 距离用户当前位置或校门/宿舍区的模拟距离。 |
| rating | number | 评分，建议 0-5。 |
| ingredients | array/string | 主要食材，用于忌口判断。 |
| avoid_tags | array/string | 可能触发忌口的标签，如花生、海鲜、香菜。 |
| dietary_tags / allergens / possible_allergens | array/null | 菜品饮食标签、明确过敏原和可能过敏原；未知风险信息用 null，不得视为安全。 |
| description | string | 详情描述。 |
| updated_at | string | 数据更新时间或模拟数据版本。 |

## 5. 接口职责划分

建议接口如下，具体命名可在第二轮开发时确定：

- `GET /api/foods`：返回餐饮数据列表，支持关键词和筛选参数。
- `GET /api/foods/{id}`：返回单条详情。
- `POST /api/recommendations`：接收用户偏好，返回 Top 3-5 推荐和推荐理由。
- `GET /api/health`：用于前端判断后端是否可用。

前端职责：

- 展示数据和交互控件。
- 收集用户偏好。
- 做基础输入提示。
- 展示接口返回的结果、空状态和错误状态。

后端职责：

- 参数校验。
- 数据读取。
- 硬约束过滤。
- 加权评分。
- 推荐理由生成。
- 统一错误响应。

数据库职责：

- 保存模拟数据。
- 支持稳定、可复现的查询。
- 不保存真实个人信息。

## 6. 推荐算法初步设计

### 6.1 硬约束过滤

硬约束用于处理“不能推荐”的条件，优先级高于评分。

- 预算：如果用户设置预算上限，`dishes.price > budget` 的菜品直接排除；预算必须为有限正数，不能用 `restaurants.avg_price` 替代菜品价格。
- 忌口：如果条目的 `ingredients` 或 `avoid_tags` 命中用户忌口，必须排除。推荐理由中不得淡化忌口风险。
- 营业状态：使用 TRUE/FALSE/UNKNOWN 三态；用户勾选“只看营业中”时仅保留 TRUE，排除 FALSE 和 UNKNOWN。
- 距离上限：如果用户设置最大距离，`distance_m > max_distance_m` 的条目排除。
- 用餐时段：如果用户选择早餐/午餐/晚餐/夜宵，条目的 `meal_periods` 不包含该时段时排除或降权。建议 MVP 中作为筛选条件处理。

### 6.2 加权评分

对通过硬约束的条目计算总分，建议初始权重如下：

| 维度 | 权重 | 说明 |
| --- | --- | --- |
| 口味匹配 | 0.30 | 命中用户偏好的口味标签越多得分越高。 |
| 评分 | 0.25 | 评分归一化到 0-1。 |
| 距离 | 0.20 | 越近得分越高。 |
| 价格 | 0.15 | 不超预算且越经济得分越高。 |
| 营业状态 | 0.10 | 营业中加分；若已硬过滤，则可作为轻微加分。 |

初始总分公式：

```text
score = taste_score * 0.30
      + rating_score * 0.25
      + distance_score * 0.20
      + price_score * 0.15
      + open_score * 0.10
```

其中：

- `taste_score`：口味命中数 / 用户选择口味数；用户未选择口味时给中性分。
- `rating_score`：`rating / 5`。
- `distance_score`：根据最大距离归一化，越近越高；无距离偏好时使用数据集内最大距离归一化。
- `price_score`：预算内先计算 `P = 100 × (1 - price / budget)`，再以 `P / 100` 归一化为 0-1，与其他维度加权；无预算时给中性分。预算非正数时拒绝输入，超预算时先过滤；不能用最低价排序替代综合推荐排序。本轮仅修订设计，不实现评分代码。
- `open_score`：TRUE 为 1，FALSE 和 UNKNOWN 不获得营业加分；若用户要求只看营业中，后两者已被过滤。

### 6.3 推荐理由生成

推荐理由必须和实际数据一致，不能生成无法从字段验证的描述。

推荐理由示例：

- “符合预算：菜品 16 元，不超过 20 元预算。”
- “口味匹配：包含微辣、面食标签。”
- “距离较近：约 280 米。”
- “评分较高：4.7 分。”
- “当前标记为营业中。”

如果字段缺失：

- 不引用缺失字段。
- 显示“该项数据暂无”，并在评分时使用保守默认值。

## 7. 非功能需求

### 7.1 可靠性

- 前端和后端都要校验输入。
- 接口失败时页面不崩溃。
- 推荐算法结果可复现，同一输入和同一数据返回稳定结果。
- 字段缺失时采用保守处理，不产生虚假推荐理由。

### 7.2 可用性

- 主流程应在一个页面内完成：输入偏好、点击推荐、查看结果。
- 筛选项命名应贴近学生日常语言，例如“预算上限”“离我近”“不吃/忌口”。
- 无结果时提供调整建议，而不是只显示空白。
- 详情入口明显，结果卡片信息层次清晰。

### 7.3 数据透明性

- 页面必须标注模拟数据、数据更新时间或数据版本。
- 推荐理由必须可解释、可核对。
- 不声称提供实时营业状态。

### 7.4 异常处理

- 空输入：返回默认推荐或提示用户可补充条件。
- 非法输入：指出具体字段错误。
- 无结果：提示放宽预算、距离、口味或忌口条件。
- 字段缺失：使用“暂无数据”展示，不崩溃。
- 接口失败：提示“服务暂时不可用，请稍后重试”。

### 7.5 隐私保护

- MVP 不需要登录，不收集真实身份信息。
- 不保存用户偏好历史。
- AI 日志和最终提交材料需要脱敏，不能暴露密钥、令牌、真实手机号等信息。

## 8. 技术方案风险

- FastAPI + Vue 前后端分离需要同时启动两个服务，演示时要注意运行步骤。
- SQLite 数据简单稳定，但不适合多人并发写入；本项目只读模拟数据可接受。
- Element Plus 能提高开发速度，但需避免页面过于组件堆砌。
- 推荐算法为规则和权重，不代表真实个性化学习，应在页面说明其局限性。
