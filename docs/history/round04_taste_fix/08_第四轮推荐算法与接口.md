## 2. 最终算法

```text
Score = 0.35T + 0.25P + 0.20D + 0.20R
T = 100 × 命中口味标签数 / 用户选择口味数
P = 100 × (1 - dishes.price / budget)
D = 100 × (1 - restaurant.distance_m / max_distance_m)
R = restaurant.rating / 5 × 100
```

- 第一阶段硬排除超预算、超距离、所选时段不支持、低于最低场所模拟评分的菜品。
- 用户要求仅看营业中时只保留精确 TRUE，FALSE/UNKNOWN 均排除；未要求时不排除，营业状态不计分。
- 严格忌口复用第三轮 restriction_status；每项限制必须为 TRUE，明确冲突、可能含有、必要风险字段未知和不识别限制均不得通过。规则未放宽。
- 口味为软偏好，不用探索页的单口味硬筛选替代推荐评分；未命中可保留，但 T=0，多选标签按命中比例计分，重复/非法标签拒绝。
- 未填写预算、口味、距离时，各自 P/T/D 取中性 50；不推断预算或近距离偏好，也不声称匹配未选条件。R 始终来自实际关联场所。
- budget 必须有限且大于零，最多两位小数，小于十亿元；距离有限且非负。零距离上限仅保留实际零距离，D=100；当前种子没有零距离，所以该条件真实返回空列表。
- 数据中的价格、评分和距离缺失/非法时，读取校验拒绝计算，API 返回 503，不补造分值。未知营业和风险字段仍可合法表示，不视为营业或安全。
- 使用 Decimal 按上述公式计算，所有维度及总分在 0-100；按未显示舍入的总分降序、菜品 ID 升序稳定排序，再截取 Top K，默认 5、仅允许 3/4/5，按 ID 去重。
- 候选不足返回实际数量及提示，空候选返回空 items 和说明；绝不自动放宽任何硬条件。

推荐理由逐条引用实际菜品价、已设置的预算、真实匹配口味、场所模拟距离和评分。评分文案为“所属场所模拟评分为 X 分”。仅已确认状态生成模拟时刻营业说明；UNKNOWN 不生成营业结论。严格忌口理由明确基于模拟配方声明且不代表现实过敏安全保证。没有随机数、真实评价或虚构理由。

## 3. API 与前端

`POST /api/recommend` 接收 JSON：

| 字段 | 类型/缺省 | 含义 |
| --- | --- | --- |
| budget | number/null | 菜品预算上限；null 不设置 |
| max_distance_m | number/null | 场所参考距离上限 |
| min_rating | number/null | 场所模拟评分最低值，0-5 |
| tastes | string[]，默认 [] | 口味软偏好，多选 |
| avoid | string[]，默认 [] | 严格排除要求，多项 AND |
| meal_period | string/null | 硬筛选用餐时段 |
| only_open | boolean，默认 false | 仅看模拟营业中 |
| top_k | integer，默认 5 | 只能为 3/4/5 |

响应包含 items、total_candidates、message、metadata。每条 item 包含 dish（带嵌套 restaurant）、score、dimensions（T/P/D/R）、reasons。非法类型、额外字段、非法值及损坏 JSON 返回 422；存储不可用/损坏返回友好 503，不泄露路径或堆栈。空 JSON 对象允许默认推荐；不是必须填满所有偏好。

Vue 推荐页读取既有 API 的词表和元数据，不新增前端模拟菜品数据。支持多口味、预算、距离、时段、最低场所评分、严格忌口、模拟营业条件及 Top 3/4/5，展示实际结果、维度分、总分和理由，可点击原有菜品详情。

包含待提交、加载、非法输入、候选不足、空结果、接口失败及重试状态。偏好变化立即取消旧请求并清除旧结果，提示重新生成；过期响应不得覆盖新条件。响应不完整或分数非法时显示友好错误。导航及首页移除过时“开发中”，卡片明确标注“场所模拟评分”。未保存偏好到数据库。

## 7. 真实问题与修复

1. 推荐页首次 apply_patch 使用同一文件的删除与新增操作，被工具拒绝：`invalid patch: multiple operations target ...Recommend.vue`。该次未写入文件，改为 Update File 成功；真实工具错误保留在原会话中，不是测试失败。
2. 首次浏览器全量运行实际 23 项失败、exit 1。API 直接请求返回 200，但页面均显示请求失败；原因是新增 POST 参数 body 被块内 `let body` 遮蔽，fetch 访问时触发暂时性死区错误。修订响应变量为 payload，新增 GET/POST/错误响应单元回归。首次完整 stdout/stderr 在 execution.jsonl，报告、截图和 trace 在 first_browser_failure/，未删掉失败断言。
3. 修复后第二次实际 23 项通过 (42.3s)；随后新增请求取消和 Top 4 场景，最终全量为 25 项通过 (45.0s)。后端首次 54 项通过，补充损坏存储用例后最终 55 项通过。
4. 收尾检查补强不完整响应/非法维度分校验，并为候选不足返回实际数量提示。这些是检查中发现的完善项，不虚构为先失败的测试。

大包体积、Starlette/httpx 弃用及 NO_COLOR/FORCE_COLOR 提示仍存在，真实输出保留；没有为消除提示更换技术栈或安装新依赖。
