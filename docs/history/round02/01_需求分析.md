# 01 需求分析

项目名称暂定为“校园食光 CampusBite”。本文件用于第一轮 AI 交互的需求分析，不代表系统功能已经实现。

## 1. 作业要求提取

### 1.1 老师要求必须完成的内容

来源：`assignment/校园美食推荐助手_大作业第一部分.docx`。

老师对系统功能的最低要求如下：

| 序号 | 必做功能 | 最低要求 |
| --- | --- | --- |
| 1 | 餐饮数据展示 | 至少 20 条餐厅、窗口或菜品示例数据；显示名称、位置、菜系或口味、人均价格、营业时间、距离、评分等信息。 |
| 2 | 搜索与筛选 | 支持关键词搜索，以及不少于 4 个筛选或排序条件，例如预算、口味、距离、评分、营业状态、用餐时段和忌口。 |
| 3 | 个性化推荐 | 用户输入偏好后返回 Top 3-5 条推荐，并为每条结果显示与实际数据一致的推荐理由。 |
| 4 | 详情查看 | 可以查看餐厅或菜品的详细信息。 |
| 5 | 异常处理 | 对空输入、非法输入、无匹配结果、字段缺失和接口失败等情况进行友好处理，程序不得崩溃。 |
| 6 | 数据说明 | 界面注明数据为模拟数据或数据更新时间，不将示例信息误认为实时营业信息。 |

老师对开发过程和学习目标的要求如下：

- 使用任意 Vibe Coding 工具完成一款可运行的校园美食推荐助手原型。
- 将生活场景转化为用户故事、功能需求和验收标准。
- 使用 AI 辅助完成需求分析、架构设计、编码、调试、测试和文档编写。
- 设计餐饮数据模型以及基于规则或加权评分的推荐排序逻辑。
- 审查、修改并验证 AI 生成的代码，形成需求-实现-测试-迭代闭环。
- 反思 AI 输出的可靠性、偏差、隐私、版权和人机协作责任。
- 技术栈和应用形态不限，建议先完成 MVP，再进行针对性迭代。

老师对最终提交材料的要求如下：

- 最终只提交三项材料：系统截图、AI 原始日志、AI 日志索引。
- 除上述三项外，不提交源码、README、需求设计说明、测试记录或演示视频。
- 系统截图提交 3-5 张，至少覆盖正常推荐流程、不同偏好条件下的推荐结果、无结果或异常输入处理。
- 截图目录命名为 `01_系统截图`。
- 截图命名格式为 `序号_场景_内容_日期.png`，序号使用两位数字，日期使用 `YYYYMMDD`。
- AI 原始日志目录命名为 `02_AI原始日志`。
- AI 原始日志应按工具和时间顺序保存，优先提交 HTML、JSON、Markdown 或 PDF；如只能截图，需连续、完整、可读。
- AI 原始日志必须保留完整 Prompt、AI 完整回复或代码建议、学生实际操作、修改内容和验证结果。
- AI 原始日志必须保留失败尝试、错误提示、返工过程和被拒绝的 AI 建议，不得只保留成功对话。
- 可以删除 API 密钥、访问令牌、真实姓名、手机号等敏感信息，但必须附 `AI原始日志_脱敏说明.md`，说明脱敏范围，且不得改变交互含义。
- 不得手工补写不存在的对话，不得把不同时段的对话拼接成一轮；如导出不完整，应在索引中如实说明。

- 最终总文件夹命名为 `学号+姓名`，压缩包命名为 `学号+姓名.zip`。

老师对 AI 交互日志的最低规范如下：

- AI 交互日志是核心证据，应从需求分析开始连续记录到最终修复。
- 至少记录 5 轮有效 AI 交互。
- 至少记录 2 轮针对性迭代。
- 至少记录 1 次 AI 错误、不完整建议或不适用方案，以及学生的人工修正。
- 保留完整 Prompt 和 AI 关键回复，记录是否采纳及理由。
- 记录涉及的文件、代码或功能变化，以及运行和测试证据。
- 可对个人信息、密钥和敏感内容脱敏，但不得伪造或删改关键过程。

### 1.2 我们自行提出的设计方案

以下内容不是老师指定的硬性技术栈，而是为降低开发风险、保证系统可运行和便于截图验收而提出的工程选择：

- 应用名称：校园食光 CampusBite。
- 前端：Vue 3 + Vite + Element Plus。
- 后端：Python + FastAPI。
- 数据库：SQLite。
- 推荐算法：硬约束过滤 + 多维加权评分。
- 数据规模：先准备不少于 20 条模拟餐厅、窗口或菜品数据。
- 页面形式：桌面浏览器优先，简洁清晰，适合课程演示和截图。
- 开发策略：先做 MVP，再逐步补全筛选、解释、异常处理和最终测试。

合理性评估：

- Vue 3 + Vite 启动快、结构清晰，适合课程项目和单页应用。
- Element Plus 能快速提供表单、表格、标签、提示、弹窗等组件，减少 UI 造轮子。
- FastAPI 接口定义直接、自动文档友好，适合推荐接口和数据查询接口。
- SQLite 无需部署独立数据库，适合小规模模拟数据和本地演示。
- 硬约束过滤 + 加权评分能兼顾“不能违反忌口/预算”等底线条件和“更符合偏好”的排序需求。

### 1.3 可选扩展功能

以下功能有助于提升体验，但不作为第一阶段必须实现内容：

- 收藏、点赞或历史浏览。
- 用户登录和个人偏好保存。
- 地图定位或真实距离计算。
- 食堂拥挤度、排队时间、实时营业状态。
- 图片上传、菜品图片管理。
- 后台管理端。
- 基于机器学习的推荐模型。
- 多校区数据管理。
- PWA 或移动端适配优化。

## 2. 用户需求分析

### 2.1 目标用户

- 在校学生：高频使用，关注价格、距离、口味、评分、营业状态。
- 新生：不熟悉校园餐饮位置和特色，关注推荐理由和详情信息。
- 校园访客：时间有限，关注距离、营业状态、易理解的推荐理由。
- 有饮食限制的用户：关注忌口、过敏、清真、素食、低辣等约束是否被严格处理。

### 2.2 核心使用场景

- 午餐或晚餐前快速决定去哪吃。
- 在固定预算内寻找评分较高或距离较近的菜品。
- 根据口味偏好筛选，如微辣、清淡、甜口、面食、米饭、饮品等。
- 排除不喜欢或不能吃的食材，如香菜、花生、海鲜、牛肉、辣椒等。
- 查看推荐结果的原因，确认不是“黑箱推荐”。
- 输入条件过严导致无结果时，获得友好的调整建议。

### 2.3 用户故事

1. 作为一名普通学生，我希望输入预算和口味后看到 Top 3-5 个推荐，这样我可以快速决定今天吃什么。
2. 作为一名预算有限的学生，我希望系统只推荐人均价格不超过预算的餐厅或菜品，这样我不会点到超出预算的选项。
3. 作为一名新生，我希望查看餐厅或菜品详情，包括位置、营业时间、价格、距离和评分，这样我可以判断是否值得前往。
4. 作为一名不吃香菜或花生的用户，我希望系统严格排除包含忌口食材的结果，这样我可以放心参考推荐。
5. 作为一名赶时间的学生，我希望按距离或营业状态筛选，这样我能优先选择近且正在营业的窗口。
6. 作为一名对推荐结果持怀疑态度的用户，我希望每条推荐都有基于实际字段的解释，例如“预算内、距离近、评分高、符合微辣偏好”，这样我能理解推荐依据。
7. 作为一名访客，我希望系统明确提示数据为模拟数据或非实时数据，这样我不会误以为营业时间和距离完全实时准确。

## 3. 需求边界

### 3.1 本项目第一阶段应覆盖

- 首页或主页面展示模拟餐饮数据。
- 关键词搜索。
- 至少 4 种筛选或排序条件。
- 偏好表单。
- Top 3-5 推荐结果。
- 推荐理由。
- 详情查看。
- 异常和无结果提示。
- 模拟数据说明。

### 3.2 本项目第一阶段不承诺覆盖

- 真实商家数据接入。
- 实时营业状态。
- 真实地图定位。
- 登录注册。
- 支付、下单、评论发布。
- 管理后台。
- 机器学习训练或大模型在线推荐。

## 4. 人工确认事项

- 是否采用建议技术栈：Vue 3 + Vite + Element Plus + FastAPI + SQLite。
- 数据粒度以“菜品”为主，还是以“餐厅/窗口”为主，或二者混合展示。
- 预算是按“人均价格”过滤，还是按具体菜品价格过滤。
- 忌口采用严格排除，是否需要对“可能含有”或“交叉污染”做提示。
- 是否需要体现本校真实食堂名称；若使用真实名称，需确认是否允许作为模拟数据使用。
